# Follow-up repeat k5: three skipped payment events

Round 2's diagnostic pass ran 17 follow-up repeats of csharp-wax-rw8 on the payment file at 8 workers and 500,000 accounts, each keeping its database, to catch a failure that could be inspected. Repeat k5, run from 05:01 to 05:17 local time on 2026-11-15, failed the gate that every payment read model row matches its payment and passed every other gate. Its record is in [results](../results/2026-11-15-round2-diag-followup-csharp-wax-rw8-batch-payments-w8-k5/run.md). Its database was kept for this analysis and dropped afterward. [round2-diag.k5-payment-gate.txt](round2-diag.k5-payment-gate.txt) is the dump taken from it for the gate that failed: the three payments without a read model row, their events, the events numbered 552,172 to 552,270 with the transaction that wrote each and whether the payment read model holds it, and the read model's nearest numbers on either side of the gap. The figures below come from that dump, from the run's record, and from the code as it stood before the fix, except where a paragraph says the kept database showed them.

## What is missing

Three payments have no row in `ar.payment_read_model`, and every other payment's row matches. All three are `payment.posted` events with consecutive global numbers, and the read model holds the payments on either side.

## Why it is the inflated mark

- **The gap ends at a logging point plus 32.** With a sequence cache of 1, `nextval()` writes a WAL record on every 33rd call. A logging call hands out a number v and leaves `last_value` at v and `log_cnt` at 32, and while it logs, the sequence's row briefly holds v plus 32. The kept database showed the sequence at the end of the run with `last_value` 1,500,000 and `log_cnt` 15, so the last logging call handed out 1,499,983. The difference between 1,499,983 and 552,190 is 947,793, which is 33 times 28,721, so 552,190 was handed out by a logging call, which put 552,222 in the sequence's row for a moment: exactly the last number skipped. A chance match would have odds of 1 in 33.
- **No checkpoint shifted the phase.** A checkpoint makes the next `nextval()` log early, which would break the arithmetic. The run's record (`db_activity.checkpointer` in its `results.json`) shows no checkpoint, timed or requested, from 11:02:28 to 11:16:17 UTC, when the head already stood at 1,500,000, so every `nextval()` after 552,190 falls in a window without one. The counters matter because `checkpoint_timeout` is 15 minutes and the run lasted about 16, so the timeout alone does not rule a checkpoint out.
- **How the bad sample became the mark.** Before the fix, the C# reader's `HighWaterMark.AdvanceAsync` read the position again inside a transaction, took that transaction's id as the boundary, and kept the position as `LastSampled`. If that read came during the logging call at about 11:03:12.497, it returned 552,222. The mark takes a pending position only once every transaction older than its boundary has finished, and the transactions that later drew 552,220 to 552,222 were newer than the boundary, so nothing waited for them. A bad sample is not always harmful. If the worker's next pass had read the sequence before it really reached 552,222, at 11:03:12.526608, that read would have been below `LastSampled`, and the reader would have treated it as a restore and reset its mark to 0, which stalls the reader but loses nothing. Here the next pass came later, the pending entry resolved, and the page was read with 552,222 as the safe position.
- **The timing fits.** The transactions that wrote 552,191 to 552,219 had written their last events by 11:03:12.52678, and the three skipped transactions were still writing at .527969, .528072, and .528488, so a page read in the 1.5 ms between saw a short page without them. The short-page rule then moved the checkpoint to 552,222. Event 552,223 lay above the mark, so the reader's next page picked it up. A worker pass that handles events does not sleep, and a busy pass of about 30 ms fits the gap between the sample and the page read.
- **Why the other gates held.** One worker pass samples one mark and uses that safe position for each projection it advances in turn (`ProjectionReader.RunOnceAsync`). The account summary projection reads only account events, and the three skipped events were `payment.posted`, so no mark could make it lose them. The account payment projection does read `payment.posted`. It held either because another worker had it claimed during that pass or because this worker reached it after the three transactions committed, at about 11:03:12.5285 to .529. The dump does not show which.
- **The race rate overstates the skip rate.** A skip needs the bad sample, a later pass after the sequence has caught up, and transactions still open in the window when the page is read. Some bad samples instead reset the mark to 0, which delays a reader but loses nothing. Reading the mark with `pg_sequence_last_value()` removes both.

This matches the mechanism that [the engine bake-off README](../README.md#round-2s-diagnostic-pass) gives for run 2 of the diagnostic pass, and the sequence-read test in [round2-diag.seq-race.txt](round2-diag.seq-race.txt), which saw the plain read return a number up to 32 ahead of what had been handed out. Run 2's database was dropped, so run 2 itself cannot be checked. Run 2 failed the account summary gate, which would have needed the same race to hit a window holding account events; that is consistent with k5, but unproven.
